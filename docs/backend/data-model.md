# Data model and domain rules

All primary keys are UUIDs. All timestamps are timezone-aware and generated by
the server. Team-local calendar decisions use the team's IANA timezone.

## Identity and teams

### User

Use a custom Django user model from the first migration.

| Field | Notes |
| --- | --- |
| `id` | UUID primary key |
| `email` | Unique, normalized login identifier |
| `display_name` | User-controlled name |
| `timezone` | IANA timezone |
| `is_active` | Authentication state |
| `created_at`, `updated_at` | Audit timestamps |

`is_me` is never persisted. The authenticated user determines who "me" is.

### Team

| Field | Notes |
| --- | --- |
| `id` | UUID primary key |
| `name` | Team display name |
| `timezone` | IANA timezone used for dates and weekly limits |
| `created_by` | User who created the team; no special schedule access |
| `created_at`, `updated_at` | Audit timestamps |

### TeamMembership

| Field | Notes |
| --- | --- |
| `id` | UUID primary key |
| `team`, `user` | Unique pair |
| `role` | `member` or `owner`; ownership only manages membership |
| `status` | `invited`, `active`, or `removed` |
| `schedule_visibility` | `private` or `team`; defaults to `private` |
| `joined_at` | Nullable until invitation acceptance |

Assignments reference the membership, not the user. This prevents data leaking
between teams when one user belongs to several teams.

## Scheduling

### ShiftType

Shift types are scoped to a membership because the product currently describes
them as "my shift types."

| Field | Notes |
| --- | --- |
| `id` | UUID primary key |
| `membership` | Owning membership |
| `code`, `label`, `color` | Display properties |
| `kind` | `work` or `rest` |
| `sort_order` | Tap-cycle order |
| `archived_at` | Soft deletion; historical assignments remain valid |

### ShiftTypeInterval

| Field | Notes |
| --- | --- |
| `shift_type` | Parent type |
| `position` | Stable ordering |
| `start_minute`, `end_minute` | Minutes from midnight, `0..1439` |
| `ends_next_day` | Whether the interval crosses midnight |

Rest types have no intervals. Work types require at least one non-overlapping
interval.

### Assignment

| Field | Notes |
| --- | --- |
| `id` | UUID primary key |
| `membership`, `work_date` | Unique pair |
| `shift_type` | Nullable only if the API uses deletion for unknown days |
| `source` | `manual`, `copied`, or `swapped` |
| `version` | Incremented on every mutation for conflict detection |
| `created_at`, `updated_at` | Audit timestamps |

An absent row means **unknown schedule**. An assignment whose shift type is
`rest` means **confirmed day off**. Never conflate these states.

Assignment-specific intervals are copied into `AssignmentInterval` when a user
overrides a day's hours. Accepted swaps exchange the effective interval payload,
so later editing a shift template cannot change an accepted or historical shift.

There is deliberately no absence-reason model. The app accepts only work shifts,
confirmed days off, and unknown days. API payloads, logs, analytics, push
notifications, and audit events must not contain medical information.

## Offers and blind requests

### SwapOffer

| Field | Notes |
| --- | --- |
| `id`, `team`, `created_by` | Identity and scope |
| `assignment`, `assignment_version` | Offered shift and optimistic lock |
| `note` | Optional; apply length limits and warn against sensitive data |
| `status` | `open`, `claimed`, `cancelled`, or `expired` |
| `claimed_by` | Set only after a successful claim |
| `created_at`, `resolved_at`, `expires_at` | Lifecycle timestamps |

The note is the only free-text field in this domain. Prefer removing it before
launch if moderation and sensitive-data handling are not ready.

### SwapRequest

| Field | Notes |
| --- | --- |
| `id`, `team`, `requester` | Identity and scope |
| `assignment`, `assignment_version` | Requester's shift and optimistic lock |
| `mode` | `rest_day` or `change_slot` |
| `status` | `open`, `accepted`, `rejected`, `cancelled`, or `expired` |
| `accepted_by` | Hidden until acceptance |
| `accepted_their_date` | Cross-day scenario date, if applicable |
| `created_at`, `resolved_at`, `expires_at` | Lifecycle timestamps |

### SwapRequestRecipient

Stores the server-selected candidate and scenario. Recipient rows are never
serialized to the requester.

| Field | Notes |
| --- | --- |
| `request`, `recipient` | Unique pair |
| `candidate_assignment`, `candidate_assignment_version` | Proposed exchange |
| `scenario_kind` | Same-day slot or cross-day rest swap |
| `status` | `pending`, `accepted`, `declined`, or `invalidated` |
| `notified_at`, `responded_at` | Delivery lifecycle |

## Authorization and privacy

- Users may write only assignments and shift types belonging to their active
  memberships.
- `private` means only the owner can retrieve exact assignments.
- `team` means active members of that team may retrieve exact assignments.
- The backend may inspect either visibility mode for blind matching; it never
  returns candidate identities or private assignments to the requester.
- Team ownership never overrides an individual's schedule visibility.
- Users outside the team receive `404`, not an existence-revealing `403`.
- Changing visibility to `private` affects all subsequent responses immediately.
  Previously viewed or screenshotted information cannot be recalled.

## Transactional invariants

- Only one assignment exists per membership and work date.
- Only one active offer/request may commit a given assignment.
- Preview results are advisory. Acceptance always recomputes eligibility.
- Claim and acceptance operations use `transaction.atomic()` and
  `select_for_update()` on the offer/request and every affected assignment.
- A claim never overwrites an existing work assignment owned by the claimant.
- Mutating endpoints accept an idempotency key so mobile retries cannot duplicate
  requests or apply a swap twice.
- Notifications are scheduled with `transaction.on_commit()`.

## Matching rules

Port the existing pure TypeScript behavior to tested Python domain services:

- only future work assignments;
- explicit rest assignments are required—unknown days are not rest days;
- at least 12 hours between consecutive workdays;
- at most six consecutive workdays;
- at least one rest day in every rolling seven-day window;
- same-day changes require different effective intervals;
- assignments in active offers or requests are unavailable;
- cross-day candidates are searched within seven days;
- requester-facing results contain a count, never candidate IDs or names;
- acceptance revalidates all rules against current locked rows.

The weekly request limit is enforced on the server using the team timezone. The
initial default is three created requests per membership per Monday-based week.
